# HOTRANK Phase 1 — Recommended Migration Waves

Every wave below is future work. Phase 1 stops at this plan and does not begin Wave 2.

| Wave | Purpose | Write surface | Rollback | Test gate | Frontend regression gate | Human/external dependency |
|---|---|---|---|---|---|---|
| Phase 2 — Backend isolation layer | Define canonical domain types, repository interfaces, mappers, feature flags, and contract fixtures | None against production; local fixtures only | Remove/disable adapter flag and retain static canonical fixtures | Typecheck, mapper contract tests, raw-row leakage check | All frozen route/viewport screenshots and smoke assertions unchanged | None beyond repository review |
| Phase 3 — Supabase foundation and auth reconciliation | Decide authoritative profile/content model; add non-destructive RLS/role/invite foundations; reconcile session refresh | Auth/profile/invite writes only after approved additive migrations | Disable beta writes; retain rows; revert feature flag; restore prior auth path | Local migration replay, RLS matrix, role-escalation negatives, OAuth callback tests | Auth gates and header/menu behavior remain pixel/interaction stable | Owner-authorized Supabase project, schema export, OAuth provider access |
| Phase 4 — Core read paths | Connect approved creators, clips, detail, and rankings through server-side read adapters | Read-only production access first | Flip reads back to canonical fixtures/static fallback | Fixture/live contract tests, safe public projection tests, score/movement invariants | `/`, `/rankings`, `/clips/[id]`, `/creators`, `/creators/[slug]`, `/search` visual regression | Reconciled remote schema and read access |
| Phase 5 — User state | Add saves, follows, profile reads/updates, and private activity projection required by V1 | Authenticated server actions/RPCs for saves/follows/profile | Disable mutation flags; preserve valid rows; replay from audit if needed | Multi-user IDOR/RLS tests, optimistic rollback tests, session-expiry tests | `/saved`, `/profile`, `/activity` route and responsive regression | Supabase role/RLS approval; privacy review |
| Phase 6 — Submission and moderation | Implement source validation, ownership declaration, metadata normalization, review queue, archive/removal | Pending submission create; moderator status writes; creator-owned safe edits | Pause submission intake; leave pending rows; unpublish rather than delete | Duplicate/URL/rights tests, moderator matrix, status transition audit, webhook-free local flow | `/submit` and detail states preserve canonical layout and copy hierarchy | Moderator/admin owner, terms/takedown policy |
| Phase 7 — Content reset and Invite 30 | Snapshot/reconcile data, remove only approved Class C fixtures, onboard ~30 real creators, publish approved content | Invite acceptance, creator onboarding, curated submission/review, activity analytics | Revoke invites, pause intake, unpublish content, restore snapshot if approved | Cohort end-to-end test with role matrix, backup restore rehearsal, analytics events | Full canonical route/viewport/console regression before invitations | Human content/rights review, remote backup/export, support owner |
| Phase 8 — Optional monetization | Only if beta evidence requires it: replace mock Dodo path with a fail-closed provider design | Server-created product/checkout and verified webhook only | Disable checkout; do not revoke historical records automatically; reconcile refunds manually | Signature/replay/idempotency/fraud/amount/ownership tests | Locked prompt presentation remains stable with explicit unavailable state | Payment-provider account, legal/tax/payout approval, security review |
| Phase 9 — Vercel and domain cutover | Establish the canonical deployment and `hotrank.xyz` relationship | Deployment promotion, env configuration, DNS/domain changes | Revert promotion and DNS/alias according to approved runbook | Build, smoke, auth, submission, read/write, error, and rollback tests | Production route/viewport/console regression against the frozen contract | Vercel HOTRANK project/team access, Supabase production access, registrar/DNS access |
| Phase 10 — Public scale | Expand signup, ingestion, storage, moderation, analytics, notifications, collections, and public operations | New public writes and provider jobs | Feature flags and staged rollout; preserve audit/data snapshots | Load, abuse, provider failure, privacy, and disaster-recovery tests | Canonical V1 remains the presentation baseline; any design change is separately approved | Product/legal/support/operations approval |

## Non-negotiable sequencing

Do not run a content reset before the Class D remote inventory is exported and classified. Do not connect the canonical frontend to the legacy tables directly. Do not enable payments, public signup, or production DNS as part of the Invite-30 wave.
